# Decode and prefill performance, v0.2.0 to v0.3.0 (2026-11-04)

SmolLM2-135M-Instruct Q4_0, one container, greedy, Chromium (Playwright),
Metal on an Apple M4 Max, f32 kernels, no subgroups, no f16. 128-token prompt,
128 generated tokens, interleaved rounds, 1-minute load 3.5 to 5.5.

| **v0.3.0** | **5359 (5152-5472)** | **580 (572-601)** |

10 interleaved rounds each (v0.2.0 against v0.3.0); the llama.cpp row is 5
rounds of `TestLLMBench` (go-wasmcontainers/gpu e2e). The 529 / 1286 of the

chunks, so the causal attention across chunks is covered).

## Profile (v0.2.0, decode at short context, p = 8)

No timestamp queries exist in go-gfx/webgpu (go-gfx/webgpu#16 is open and the
remote stream has no query-set command), so time per class is by bisection: the
decode time with the class left out (`generate bench -skip CLASS`), minus the
decode time with all of it. Classes overlap a little, so the figures are not
exactly additive. 4.45 ms per token in all; 0.66 ms with no dispatch at all
(recording, crossing, read-back).

| class (dispatches per token) | ms per token |
|---|---|
| matvec Q4_0 (210) | 1.47 |
| attention (30; serial over the context, one workgroup per head) | 1.26 |
| RMSNorm (61) | 0.63 |
| argmax (1 workgroup over 49152 logits) | 0.29 |
| SwiGLU (30) | 0.21 |
| RoPE + KV append (30) | 0.11 |
| matvec Q4_1 (down, some layers) / Q8_0 logits | 0.11 / 0.11 |

A tiny dependent dispatch costs about 3.7 us (RoPE: 30 dispatches, 0.11 ms), so
405 dispatches were a floor of about 1.5 ms before any work.

## Kernel design

* K1..K5, generated per model: dimensions are WGSL constants. A workgroup of WG
  invocations computes WG/TPR output rows; TPR invocations share a row and each
  loads whole 16-byte Q4_0 blocks (`vec4<u32>`); the input vector is staged once
  in workgroup memory, in tiles when the adapter's workgroup-memory limit is
  smaller than the vector; partial sums are added by a tree reduction in
  workgroup memory. WG, TPR and the tile come from the adapter's limits; nothing
  is tuned to Apple values. The summation order depends on WG and TPR only.
* RMSNorm is recomputed by every workgroup that needs it (576 floats), the
  SwiGLU is the epilogue of the gate/up kernel (a workgroup computes the same
  rows of gate and up), RoPE and the KV append are the epilogue of the QKV
  kernel. Q, K, V and gate, up are concatenated at load time.
* Layers whose matrices are not Q4_0 (down may be Q4_0 or Q4_1) keep the
  v0.2.0 kernels; those models run one token at a time.
* Decode: up to 8 tokens per submit, each sampled on the GPU from the one
  before; after an end-of-sequence token at most 7 tokens were computed for
  nothing.

## Maximum loop iterations per invocation (ctx 512, WG 64, TPR 8)

Per loop: at most 16 (K2: `HD/4` = 16 for the dot product and 16 for the V
sum; K3 merge: `ctx/WG` = 8 chunks, twice). Per invocation, loops nested
(K3: 3 staging iterations of the merge, 2 x 8 chunk steps each, plus 3 blocks
and 3 reduction steps): about 60. K5: 6 staging + 6 blocks + 3 reduction. The
K3 merge grows with `ctx/WG`. Largest submit of the bench: 28 ms (budget
500 ms); a 64-token prompt chunk is about 12 ms of GPU time.

## Structural limit

Per-token GPU time is now bounded by dependent dispatches: 156 per token at
about 10 us each in the kernels, against 3.7 us for an empty one. Each layer
needs five (a residual add of the whole vector separates K3 from K4 and K5
from the next K1, a global dependency a workgroup cannot cross without a
second dispatch). The weights are 76 MB per token: at the machine's memory
bandwidth that is about 0.2 ms, so the floor is dispatch latency and the
reduction barriers, not bandwidth.

  a separate merge, the same idea as K2 + the merge in K3).
* Not opened in this work: WebLLM / TVM sources (not cited).

## Not measured

Firefox: the llm e2e lane drives Chromium only; Firefox is known to resolve a
submit in 200 ms steps (gpu#25), which the 8-token decode and 64-token prefill
submits amortise, but this is not measured. No NVIDIA or AMD adapter was run.

## Reproduce

`go-wasmcontainers/gpu` e2e (`LLM_MODELS`, `LLM_REPO`, `LLM_BENCH=1`):
`go test -tags e2e -run 'TestLLMOracle|TestLLMShaders|TestLLMBench' ./e2e`.
Profile: `generate bench -skip CLASS`; A/B: `-nofused`, `-tpr`, `-batch`,
`-prefillbatch`.
