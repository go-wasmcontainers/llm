# Qwen2.5-0.5B-Instruct Q4_0 (v0.4.0), 2026-11-04

Chromium (Playwright), Metal on an Apple M4 Max, f32 kernels, one container,
greedy, 128-token prompt and 128 generated tokens, 5 interleaved rounds against
llama.cpp 0.8.0 on one CPU core (`llama-bench -t 1 -ngl 0`, same session),
1-minute load 5.9 to 6.5.

| | prefill tok/s (p50, min-max) | decode tok/s (p50, min-max) |
|---|---|---|
| container v0.4.0, WebGPU, f32 | 1908 (1899-1918) | 350 (340-354) |
| llama.cpp CPU, one core | 426 (424-432) | 161 (160-162) |
| WebLLM q4f32_1 (docs/llm-baseline, not re-run) | 2184 | 177 |

The container decodes 2.2 times faster than the one-core reference and
prefills 4.5 times faster; WebLLM's prefill is 14 percent ahead (not re-run, so
only indicative). SmolLM2-135M is unchanged by this release (555 against 554
tok/s decode, 5392 against 5374 prefill, 6 interleaved rounds against v0.3.0;
oracle 32/32).

## What differs from SmolLM2 (opened: GGUF metadata and llama.cpp v0.8.0)

* `src/models/qwen2.cpp`: the qwen2 graph is the llama graph with the QKV
  projections added to separate biases (`attn_q.bias`, `attn_k.bias`,
  `attn_v.bias`, F32, from `build_qkv` in `src/llama-graph.cpp`), RMS norms,
  SiLU gate, and an output matrix `output.weight` used when present, the token
  embedding when not (`TENSOR_DUPLICATED`).
* `src/llama-model.cpp` (`llama_model_rope_type`): `LLM_ARCH_QWEN2` has rope
  type NEOX: the pairs are elements i and i+64 of a head, not 2i and 2i+1.
  Metadata prefix is `qwen2.`; `rope.freq_base` is 1e6.
* `src/llama-vocab.cpp` (`LLAMA_VOCAB_PRE_TYPE_QWEN2`): its own pre-tokenizer
  regex (case-insensitive contractions, one optional non-letter before a word,
  single digits, `\s*[\r\n]+`), implemented by hand in `splitQwen2`.
* This file: 24 layers, 896 embedding, 14 heads of 64, 2 KV heads (GQA 7),
  feed-forward 4864, vocabulary 151936, context 32768. The token embedding is
  Q4_0 and `output.weight` is a separate Q8_0 matrix (the SmolLM2 file ties a
  Q8_0 embedding). All 24 layers are Q4_0, including `ffn_down`.

## What changed in the code

* Config: `qwen2` architecture, NEOX rope, biases, separate output matrix.
* Tokenizer: the qwen2 pre-tokenizer; 7 corner cases (contractions, newlines,
  spaces runs, digits, accents, CJK, emoji) and the four prompts give the ids
  of llama.cpp's `/tokenize`.
* CPU path (the oracle): NEOX rope, biases, a Q4_0 embedding, the output matrix.
* GPU: the rows of Q and K (and their biases) are reordered at load inside each
  head so that the NEOX pairs become adjacent pairs; the fused QKV kernel then
  rotates adjacent pairs as before (q.k scores are unchanged by a permutation
  applied to both). The biases follow the norm weights in the scale buffer and
  are added before the rotation. A Q4_0 embedding gather kernel. The output
  matrix (136 MB of quants, above the 128 MiB binding size) goes to the GPU in
  row ranges bound with an offset into the logits. Layers that are not fusable
  are refused for a model that needs biases or NEOX rope.
* `check` lowers the collector's heap growth: the CPU path holds the 428 MB
  model in guest memory.

## Correctness

Strict oracle (llama.cpp on the same weights dequantised to F32,
`llama-quantize --allow-requantize ... F32`; `--cache-type-k f32
--cache-type-v f32 -fa off`): the Go f32 path gives 32 of 32 greedy tokens on
4 of 4 prompts (step-1 log-probability differences at most 2.4e-5); the GPU in
Chromium gives 32 of 32 on 4 of 4; GPU against the CPU path: logits within
4.3e-6 relative, 16 of 16 tokens, on a 4-token and a 137-token prompt (two
prompt chunks of 64, three attention chunks). The tiled path of the
down projection (4864 inputs do not fit one tile of the 16 KiB workgroup
memory: two tiles) is exercised here for the first time.

## GPU memory

`MemoryUsed` after the load, context 512: 479,751,852 bytes (457.5 MiB):
weights about 440 MB (token embedding 85, output matrix 153, 24 layers 200),
KV cache 24.6 KB per token (12.6 MB at 512), prompt-chunk and activation
buffers. `--gpu-memory 512m` is enough at context 512 (the long-prompt check
ran with it); 1 GiB leaves room for a context of about 20000 tokens. Well under
1.5 GiB. Weights stream in 16 MiB pieces; the guest never holds the model.

## Profile (ms per token of 2.85, decode at context 128 to 256, 8 tokens per submit)

By bisection, as for SmolLM2 (classes overlap a little):

| class | ms per token |
|---|---|
| output matrix, Q8_0, 151936 rows (1 dispatch, v0.2.0 kernel) | 0.80 |
| K4 gate/up/SiLU | 0.62 |
| K5 down (tiled) | 0.50 |
| K3 merge + output projection | 0.23 |
| K1 QKV + biases + RoPE | 0.21 |
| argmax (2 stages) | 0.01 |
| no dispatch at all | 0.08 |

The Q8_0 output matrix is bound by memory and by its kernel: 145 MB per token
is 0.36 ms at 400 GB/s; the one-workgroup-per-row v0.2.0 kernel takes 0.8 ms.
A vec4 Q8_0 kernel in kernels/q4's style is the next gain (about 0.4 ms, to
about 400 tok/s). Prefill (1908) is bound by the 64-token chunk reading every
weight once and the output matrix applied to one token only.

## Maximum loop iterations per invocation (ctx 512, WG 64, TPR 8)

Per loop: 38 (argmax stage 1, slices of 2374 logits for 64 invocations), 30
(K5: 15 blocks per tile, two tiles; 15 staging iterations per tile), 16 (K2
and the K3 merge at 8 chunks), 14 (embedding gather and the RMSNorm of the
head). Per invocation, nested: about 70 (K5: 30 staging + 30 blocks + 3
reduction; K3: 4 staging x 16 merge). The gpu loop-budget rewriter reported 19
modules, 11 rewritten, 4 refused after the rewrite (kept as written) in these
runs, 0 truncations; which four is not reported by the host.

## Reproduce

`go-wasmcontainers/gpu` e2e with
`LLM_MODELS=DIR LLM_MODEL_FILE=qwen2.5-0.5b-instruct-q4_0.gguf
LLM_REGISTRY_NAME=qwen2.5-0.5b-instruct-q4_0
LLM_ORACLE_FILE=oracle-qwen2.5-0.5b-dequant-f32.json LLM_GPU_MEMORY=512
LLM_LONG_REPEATS=8` and `-run 'TestLLMOracle|TestLLMCheckLong|TestLLMBench'`
(`LLM_BENCH=1`); the CPU oracle: `LLM_MODELS=DIR go test -run
TestOracleQwenDequantizedF32 .` with the two GGUF files in DIR.
